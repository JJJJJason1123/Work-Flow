# 可复现的 Agent 协作工作流

本仓库描述一套“一个管理入口、明确执行环境、逐项推进、按证据交付”的协作方法。目标是让接手的 Agent 不依赖私人聊天历史，也能理解工作分工、复现派发与验收过程，并在故障或中断后正确恢复。

这是**工作流文档与空白模板**，不是运行程序、安装包或已验证兼容所有平台的自动化系统。阅读文档不会自动获得电脑访问权、模型权限、消息发送能力或后台唤醒能力。每个平台的实际能力都必须在使用时验证。

## 一分钟理解

- 用户决定目标、约束、授权和重要业务取舍。
- 管理者对完整结果负责，不只负责“把提示词转发出去”。
- 执行者在明确的电脑、工作目录和对话里完成一项有边界的任务。
- 审查者在有必要时独立检查结果，不以执行者的自我报告代替验证。
- 同一项目默认一次只执行一项业务修改；不同任务的并行必须有独立性和明确范围。
- 发送成功、目标收到、任务完成、验收通过、上线成功是不同状态。
- 失败先判断作用范围和是否已经产生副作用，再决定重试；不确定是否送达时不得直接重复发送。
- 用户纠正、暂停或取消时，先确认最新范围，及时转达并核实执行端状态。

## 快速复现路径

1. 指定一个管理入口、一个执行端和一个测试范围，不从复杂多 Agent 团队开始。
2. 在仓库之外的私有记录中填写[环境登记模板](templates/environment-register.md)。公开仓库只保留空模板。
3. 明确需要原生本地对话、在本机执行的托管任务，还是云任务。三者不可混称。
4. 逐级验证：电脑可连接 → 工具存在 → 无害读取成功 → 经用户授权的测试消息送达 → 目标回执可读。
5. 按[任务单](templates/task-brief.md)填写一个边界明确的工作项，确认接收后再进入执行。
6. 执行结束后按[验收记录](templates/acceptance-record.md)核对最终版本、结果和限制。
7. 更新[状态与交接记录](templates/status-handoff.md)，向用户交付可使用的结果，再决定下一项。
8. 发生故障时使用[诊断记录](templates/incident-record.md)，不要把未经证实的假设固化成配置。

## 仓库使用方式

本仓库保存通用规则；实际运行数据、任务内容、用户批准记录和设备映射保存在获准的私有位置。Agent 开始工作时应读取当前任务的私有记录，但不把它们复制进公共仓库。

本仓库没有提供具体源代码、命令脚本、任务案例、真实电脑名称、路径、账号或凭据。创建本地文件不等于授权发布到 GitHub。本仓库也未自动初始化 Git、创建远端或上传。

## 完成的定义

一个工作项只有在范围内结果已存在、必要验证完成、用户能够取得结果、残留限制说明清楚时，才可标记交付。需要人类验收、生产部署或专业签署的工作，分别保留对应状态，不以“代码完成”覆盖这些关口。
