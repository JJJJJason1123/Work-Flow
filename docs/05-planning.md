# 05 排序与规划

[返回入口](../README.md)

## 默认逐项推进

同一项目的业务修改默认串行。一次派发一项可独立验收的工作；完成技术验证及约定验收后才进入下一项。不要将一份长待办直接整体丢给执行者，也不要把完整问题拆成大量需要用户协调的小动作。

“逐项”不排斥一个工作项内部的必要步骤，例如诊断、修改、测试和交付。本质是保持范围、责任和验收边界清楚。

## 排序原则

1. 阻断日常使用、数据正确性或已承诺交付的问题。
2. 有明确根因、规则已确定且影响范围可控的修复。
3. 会影响多个后续事项的基础规则或数据关系。
4. 常规流程优化。
5. 独立的布局与便利性改善。

优先级不是绝对标签：风险、依赖、用户最新方向和等待成本可能改变顺序。改变顺序时记录理由。

## 先定规则，后做联动

当金额口径、权限归属、角色定义或聚合方式会传播到其他功能时，先通过一个去敏示例明确规则，再实现依赖项。避免在每个页面里分别猜测同一个概念。

问题列表要区分：缺陷、需求、配置/部署问题、待业务决定、研究假设。不能把所有反馈都当成代码缺陷。

## 阻塞时如何继续

一个事项等待决定时，不应自动阻塞所有独立工作。管理者可把它标为等待，明确原因，再逐项处理不依赖该决定且已授权的内容。不能以“绕过阻塞”为由改变用户保留的决定。

## 何时允许并行

仅当任务输入、输出和修改范围独立，且不会争抢同一数据或运行环境时考虑并行。例如独立资料研究或对最终成果的审查。并行前应明确冲突处理、结果合并责任和总资源预算。

同一文件、同一数据库、同一 UI 会话或同一有状态工具的写操作通常需要串行或显式锁定。不同对话不等于不同文件系统。

## 控制成本

设定检查边界和停止条件。对重复失败先总结证据，再改变实验设计；不要让多个 Agent 重复同一搜索。记录关键结论、已经尝试且失败的方法和原因，让接手者不重走弯路。
