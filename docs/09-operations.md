# 09 运行维护与指标

[返回入口](../README.md)

## 状态记录

每个工作项最少保留：目标、范围、授权、当前版本、执行位置、最新状态、最后证据、阻碍、下一步、责任方。按需记录，不要求为微小事项建立复杂数据库。

工作队列与私有承诺列表可以分开，但必须避免同一事项出现冲突状态。任务完成时更新真正使用的待办，不只在聊天中说“记住了”。

## 主动跟进

执行者应报告完成、阻碍和需要决定的变化。若平台支持完成通知，先验证再依赖；不支持时设置明确的检查时间或由管理者定期读取。检查频率应与任务时长和成本相称，不持续高频轮询。

用户要求安静时，减少进度消息，仍保留必要的权限或重大风险提示。状态更新回答“完成了什么、还差什么、是否需要用户行动”，不堆叠技术日志。

## 成本与延迟

优先衡量端到端交付成本，而不是单次模型调用速度。管理成本、重复尝试、等待审批和错误环境都可能比推理时间更大。对简单工作使用简化路径，对高风险工作保留足够验证。

## 指标

| 指标 | 用途 |
|---|---|
| 正确路由率 | 是否送到指定设备和对话 |
| 投递确认率 | 是否能明确确认收到 |
| 重复动作次数 | 是否存在不安全重试 |
| 一次验收通过率 | 输出与需求是否一致 |
| 用户介入次数 | 是否真正减少协调负担 |
| 端到端时长 | 包含等待、返工和交付 |
| 总资源消耗 | 包含管理、执行、审查与重试 |
| 恢复成功率 | 暂停或断线后是否正确继续 |

不为了漂亮指标省略必要验证，也不把一个项目的结果推广到所有任务。

## 维护节奏

出现错误路由、重复派发、误报完成或反复返工后，补一条可复用教训，说明触发条件与预防方式。不要把私人事件原样写入公共文档。更新规则后检查是否与旧规则冲突，并保持模板同步。

## 退出条件

任务交付、用户取消、范围外阻碍或授权结束时停止相应工作。监控任务应有明确停止条件。维护工作流不等于无限扩大到其他项目或账户。
