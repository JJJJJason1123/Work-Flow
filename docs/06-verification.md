# 06 验收与交付

[返回入口](../README.md)

## 验收从派发前开始

任务单应定义可观察的成功条件、必须保留的行为、受保护资料及不在范围内的事项。没有验收条件时，“做完”容易只是实现者的主观判断。

## 证据层次

| 陈述 | 所需证据 |
|---|---|
| 工具存在 | 当前工具目录中实际列出 |
| 工具可用 | 对正确目标的实际调用成功 |
| 已发送 | 发送结果明确；必要时再查目标 |
| 已收到 | 目标回执或目标端内容可核验 |
| 已实现 | 最终成果确实存在于指定工作位置 |
| 技术验证通过 | 对最终版本的相关检查通过 |
| 用户验收通过 | 用户对约定验收范围明确确认 |
| 已部署 | 目标运行环境加载了指定版本并核查 |
| 可持续恢复 | 经约定重连/重启或恢复场景验证 |

## 最小足够验证

验证深度匹配风险。小范围文档修改检查内容、链接和保存即可；复杂系统变化应检查受影响链路、边界与失败行为。不能使用管理员权限通过来替代目标角色测试，也不能只看界面成功提示而不确认持久结果。

必要时包括保存后重开、取消/返回、重复提交、无授权访问、历史数据兼容、失败恢复等场景。不是所有任务都要全部执行；选择与本次变化有因果关系的检查，并说明未覆盖范围。

## 独立性与最终版本

审查者应检查最终成果和证据，不只复述执行者报告。修正后需要重新验证受影响部分。测试结果必须标明对应版本、环境和时间，旧结果不能自动证明新版本通过。

## 性能验证

以用户实际体验的指标为准，明确从何时开始、何时结束、使用哪个界面或统计。不能拿内部函数耗时代替端到端耗时。比较前后要说明样本、输入和环境是否可比；一次结果只能说明该次观察，不能宣称稳定提速比例。

## 报告格式

使用[验收记录模板](../templates/acceptance-record.md)。结论分别列出通过、失败、未运行与待用户验收。若风险或资料限制阻止全面验证，交付时直接说明；不要以“应该可以”填补缺失证据。

## 交付后

结果应位于用户期待的位置并可打开使用。草稿完成不等于已发布；文件已保存不等于已上传；本地功能完成不等于上线。残留任务保留独立状态，避免主任务勾选后被遗忘。

## 固定角色团队的复审

[本地编码团队方案](11-local-coding-team.md)给出审查不放行后的职责和交接顺序。返工必须对应原发现与新版本；复审记录区分亲自复现、仅查阅证据和未验证，不能用旧版本结论放行新改动。
