# 11 可选：固定角色的本地编码团队

[返回入口](../README.md) · [角色职责](01-roles.md) · [生命周期](04-lifecycle.md)

## 定位与验证边界

本方案把管理、实现与独立审查分开，适用于持续维护、前后端分工明确、需要反复审查的本地项目。它是可选工作组织方式，不替代最小团队原则，也不要求小修改建立完整团队。

截至本次整理，使用者已确认实际环境中的任务派发、独立代码审查、不放行后的继续修改、人工确认分歧均可用。本次只读管理对话进一步观察到“修改后提交复审、复审仍不放行、管理者继续修正并取得用户业务决定”的记录。该观察不等于重新运行实现、测试或审查，也不表示正在进行的全部工作已完成。

此处沉淀的是上述协作机制，不公开原始对话、实际任务、项目规则、设备和对话标识。跨设备兼容、重启恢复、后台唤醒、技术权限隔离、生产发布以及完整系统测试，均不能由这次观察推定为已验证；在自己的环境中须分别验收。

## 采用前提

1. 用户已同意项目范围、执行位置和团队方案。使用现有对话时先确认其身份及职责，不因名称相似直接派发。
2. 本地管理对话实际具备向目标执行对话发送任务、读取结果的受支持能力。逐级完成[能力验收](02-setup.md)；仅列出工具不代表调用可用。
3. 明确原生本地对话、在本机执行的托管任务与云对话的区别。文档描述本地团队，不代表远端管理入口天然拥有本地消息权限。
4. 建立私有角色登记、任务状态及证据位置。实际路由信息不写入本公开仓库。
5. 有真实且可核验的独立审查对话。由同一模型在一条回复中模拟多个角色，可以辅助规划，但不能冒充独立执行或独立代码审查。

## 角色配置

| 角色 | 输入与产出 | 边界 |
|---|---|---|
| Manager | 接收用户目标，拆分排序，派发任务，收集证据，处理分歧与返工，更新待办并统一交付 | 本配置下不直接修改业务代码；不能把已派发当成完成 |
| Backend Coder | 实现获准的后端范围，提供变更、测试、限制及交接材料 | 不越过业务决策，不自行勾选整项验收完成 |
| Frontend Coder | 实现获准的界面范围，验证真实交互与相关权限，提供交接材料 | 不仅凭截图或成功提示声称链路完成 |
| Code Reviewer | 只读检查需求、实际最终差异和证据，输出发现、放行范围或不放行理由 | 不修改业务代码、不自行派任务；不以执行者总结代替独立检查 |
| 用户 | 决定重大业务取舍、授权边界及必要的体验验收 | 不承担例行派发与追踪工作 |

只用到一个实现方向时，另一个 Coder 不必参与。Reviewer 由 Manager 提供自包含材料，不要求阅读其他执行对话；这是职责约束，不应宣称系统已实现技术上的访问隔离。

规划类技能可用于改进任务单与复盘，但它本身不等于投递渠道。实际派发必须由当前可用且获准的工具完成，并留下可核验回执。

## 建立团队

1. Manager 核对项目入口、现有修改、受保护资料及工作队列。
2. 在获准环境中准备需要的角色对话，先明确职责、允许范围和回报对象，不立即批量派发业务任务。
3. 在私有登记中绑定环境、对话类型、目标标识和角色。先用获准的无害测试确认发送、接收、回读链路。
4. 约定实现者返回 Manager，Reviewer 返回 Manager，由 Manager 向用户交付。不要让用户在多个角色间搬运提示词。
5. 同一项目默认一次一个完整工作项。该项如需前后端配合，由 Manager 明确依赖、接口与修改边界；有共享文件冲突时串行处理，不把共享目录误认为隔离工作区。

## 单项任务的完整循环

### 1. 建立任务与基线

Manager 使用[任务单](../templates/task-brief.md)记录目标、允许修改范围、不做事项、验收条件、受保护行为、当前版本或差异基线、授权和人工关口。先读现有资料，常规技术选择自行判断，重要业务规则不得猜测。

### 2. 真实派发与接收

向正确的 Coder 发送自包含任务。将任务标识、派发版本与当前环境绑定。收到回执后核对范围一致；已发送、已收到、已开始分别记录。不确定是否送达时先查询，不重复投递。读写接口受限时按[环境与派发](03-routing.md)处理，不偷偷换通道。

### 3. 实现与自测

Coder 在范围内修改，保存变更和测试证据，报告失败、未运行及未覆盖项。自测完成只进入“待验证（待独立审查）”，不是自动完成或上线。若依赖尚未满足，列明已完成部分与下一步，不以一句阻塞报告结束全部责任。

### 4. 独立审查

Manager 给 Reviewer 提供验收条件、最终差异基线、影响范围、实现报告及证据位置。Reviewer 检查实际成果，按风险补充必要验证，并清楚区分亲自复现、仅阅读证据和无法验证。

审查结论包括：允许放行的范围、阻塞问题、非阻塞建议、证据不足项和剩余人工关口。只验证部分不能放行整项，代码审查通过不等于全系统功能测试或部署通过。

### 5. 不放行 → 返工 → 再审

Manager 汇总同一轮阻塞发现，给原责任 Coder 明确问题、预期行为与回归要求，避免未收齐结论就碎片化连续派发。任务回到“执行中（返工）”，保留原验收条件及审查记录。

Coder 逐条回复修正情况和新证据；对不同意的发现给出证据，不自行关闭。Manager 将新版本与上轮发现一并交 Reviewer 复审。复审检查原阻塞项及修改影响范围，不能沿用旧版本通过结论。若仍不放行，继续这个循环；出现范围变化或关键分歧时进入决策分支，而不是为了结束而降低标准。

### 6. 人工分歧处理

技术问题先依证据解决。若需要选择业务语义、数据归属、不可逆处理或用户保留的决定，Manager 用用户理解的语言说明事实、选项、影响和推荐，询问一个足以推进的问题。

等待期间只暂停受该决定影响的部分；不受影响且已授权的工作可以继续。用户答复后，将原问题、明确答复和最新范围完整交给对应 Coder，再核对后续实现是否遵守决定。新的实质变化仍须重新确认，不能把一次业务答复扩张为无限授权。

### 7. 收口与下一项

独立审查满足约定后，Manager 核对完整请求及最终版本，更新真正使用的待办和[验收记录](../templates/acceptance-record.md)。需要体验验收、生产部署、专业签署或全系统测试时保留单独关口与负责人。向用户报告结果、验收入口和残余限制，再进入下一工作项，不一次抛出所有无关任务。

## 状态映射与责任

以下是[统一生命周期](04-lifecycle.md)的细分标签，不是另一套相互冲突的状态表。

| 场景 | 主状态／标签 | 下一步责任 |
|---|---|---|
| 任务已发但无接收证据 | 投递待确认 | Manager 先查询 |
| Coder 自测完毕 | 待验证／待独立审查 | Manager 提交，Reviewer 检查 |
| Reviewer 不放行 | 执行中／返工 | Manager 明确范围，Coder 修正 |
| 新版本提交复审 | 待验证／复审 | Reviewer 检查新证据及受影响行为 |
| 等待用户业务选择 | 等待外部条件／待用户决定 | Manager 记录问题、阻塞范围与恢复条件 |
| 技术关口通过，仍需体验确认 | 待用户验收 | Manager 提供验收入口 |
| 本轮约定成果齐备且已交付 | 已交付 | Manager 更新待办并判断下一项 |

## 复现验收与失败处理

在自己的环境中，先验证一个边界明确的小任务，确认路由、接收、实现、自测、独立审查和交付记录连贯。对不放行返工与人工分歧，可用获准的受控演练验证，不能为了测试故意向生产代码引入缺陷。

- 送达不确定：核查目标消息与状态，不重复派发。
- 审查证据不足：补证据或保留待验证，不伪造通过。
- 多人改动冲突：核对真实差异，暂停冲突写入，不覆盖他人修改。
- 执行者停止或中断：Manager 先确认已生效部分，再按[恢复规则](07-recovery.md)续接。
- 反复不放行：归纳共同根因；若验收本身矛盾或范围变更，向用户提出具体决策，不无限扩张团队。
- 后台提醒或自动恢复未经实际验证：不得承诺无人值守也能持续推进。

本配置的退出条件是本轮约定交付、用户暂停/取消或需要尚未取得的授权。配置团队不是扩大项目范围、发布代码或复制私有资料的许可。
