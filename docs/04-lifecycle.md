# 04 任务生命周期

## 状态与进入条件

| 状态 | 含义 | 下一步责任 |
|---|---|---|
| 待澄清 | 缺少会改变执行的必要信息 | 管理者先查已有资料，只问剩余关键问题 |
| 待排队 | 范围与验收已明确，尚未轮到 | 管理者维护依赖和优先级 |
| 待投递 | 已选择目标，但未确认收到 | 管理者执行投递与回执核对 |
| 投递待确认 | 可能送达，证据不够 | 管理者先核查，不重复发送 |
| 已接收 | 执行者确认任务和环境 | 执行者开始或说明阻碍 |
| 执行中 | 正在进行范围内工作 | 执行者推进，管理者保持可联系 |
| 等待外部条件 | 等权限、资料、设备或决策 | 明确等待项、负责人和恢复触发 |
| 部分完成 | 仅部分成果完成或部分动作已生效 | 管理者核实已生效部分与剩余范围，安排验证并继续获准且未阻塞的部分，避免重复执行 |
| 失败 | 本次尝试未达到约定结果 | 管理者核实错误与副作用，选择授权范围内的恢复方案或升级，记录下一步与负责人，不自动视为任务结束 |
| 待验证 | 执行结束，等待结果检查 | 指定验证者 |
| 待用户验收 | 技术验证完成，仍需用户确认体验/业务/专业结果 | 管理者提供明确验收入口 |
| 已交付 | 本轮约定成果已交付，限制已说明 | 管理者关闭并选下一项 |
| 暂停 | 用户要求或明确决策暂缓 | 保存状态，不自行恢复 |
| 取消 | 用户撤销后续工作 | 停止可停止动作并报告已生效部分 |

“已交付”不自动代表生产发布或专业签署完成。任务若本来只要求研究报告，报告交付即可结束，不擅自进入实现。

## 标准流程

### 受理

短而明确地回应要做什么。读取已有上下文，确认目标、约束和交付位置。对明确请求不反复问同样问题；对不可逆或高影响决定遵守必要审批。

### 准备与执行

建立任务单、选择正确环境、记录初始状态。执行者应独立处理常规技术选择，遇到关键业务取舍才升级。长任务需要可恢复的检查点，但不要求每个小动作写一份报告。

### 验证与交付

核对结果与完整请求，而不是只看部分测试。收集用户能使用的文件、页面或结果。向用户明确完成内容、未验证项和剩余阻碍，然后更新状态。

## 持续推进

已授权且不被阻塞的下一步应继续，不必等用户重复催促。若任务需等待，只有真正配置了支持的唤醒/计划/通知后才能承诺稍后检查；否则说明用户需要何时重新发起。

收到委托报告后先核对：是否满足全部请求？是否已有副作用？是否存在仍可继续的部分？执行者结束并不自动结束管理者责任。

## 变更与撤销

用户更正名称、目标设备或范围时，以最新指令为准，及时转达执行端。取消时先说明已知状态，再停止可停止部分，最后核实结果。不能保证撤销已经发送的消息或已经完成的外部操作。
