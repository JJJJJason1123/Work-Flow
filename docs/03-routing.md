# 03 环境与派发

[返回入口](../README.md)

## 派发前的四项绑定

每次派发绑定：**用户授权范围 → 目标设备 → 目标对话类型及身份 → 工作范围**。这四项中任意一项不确定且影响结果，就先补证据。状态刷新后只核对可能变化的项，不重复无价值的全量检查。

发送前检查：
- 用户最新指定的是哪台设备，而不是他从哪台设备发送消息。
- 目标是既有对话还是新对话；是否属于某个项目。
- 对话名称是否可能重复；能否用受支持的标识核实。
- 是继续任务还是新任务；是否会重复已经生效的工作。
- 已有任务是否运行、等待批准或停止；不能把新消息排队当作对方已执行。
- 该路径是否在当前上下文可用，是否满足用户的禁用方式要求。

## 路径选择

优先使用能完成任务的受支持直接接口；用户指定中转时通过指定中转。直接接口与中转都不可用时，可说明人工转交或获准界面操作的方案。不能为了“完成”而改变用户保留的执行位置、对话类型或禁止方式。

一个允许云任务的指令不自动允许改用本地；反之亦然。一个执行端在线不代表其所有应用都可控或所有对话可读。

## 投递协议

1. 生成工作项标识和本次派发标识，保存在私有记录。
2. 任务单明确范围、禁止事项、验收条件和回复位置。
3. 只发送一次。
4. 记录工具响应：成功、失败、部分成功或不确定。
5. 有支持的读取方式时，核对目标回执；没有则明确未确认送达。
6. 按回执证据记录状态：仅确认收到时记为“已接收”，明确已开始时记为“执行中”，受阻等待时记为“等待外部条件”并记录等待项；不得把确认回执直接视为已开始。任务结束另行验收。

回执至少包含工作项标识、收到的范围、实际环境和是否开始执行。执行者认为环境或范围不一致时应停止，而不是迁就错误目标。

## 重试与去重

- 明确未发送：可以在原授权内修复后再试。
- 明确收到：不要再发送相同任务；需要调整时发送带版本说明的更新。
- 结果不确定：先查目标历史、回执或动作结果。无法核实时标为投递待确认，并说明重复风险。
- 不同中转、不同对话与备用方式共享同一任务标识，防止双执行。
- 修改指令应保留原工作项，注明哪些要求替代旧版本；不要让两个执行者分别实现相互冲突的版本。

## 发送失败不应扩大工作

诊断只触及必要层次。不得把短暂工具故障变成未经授权的系统重装、全局权限调整、凭据转移或无限期监控。具体失败处理见[恢复章节](07-recovery.md)。
